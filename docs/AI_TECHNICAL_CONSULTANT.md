# AI Technical Sales Consultant AutoTerra

Изменения в существующем Django backend, ветка `adilhan_new`.
API остаётся `POST /api/ai/chat/`; отдельный проект и новый AI endpoint не создаются.

## Поток обработки

1. Сохранить исходный вопрос и ответ в существующих AIConversation/AIMessage.
2. Определить intent без отдельного LLM-вызова: general_brand, product_lookup,
   assortment, product_selection, technical_problem, application, compatibility,
   alternatives, comparison или workflow.
3. Получить разрешённый пользователю QuerySet каталога. Найти и ранжировать
   до 20 кандидатов за проход; выбрать максимум шесть товаров.
4. По вопросу и найденным товарам искать KnowledgeChunk и approved KnowledgeCard.
   Используются русский PostgreSQL FTS и отдельная ветка title/original_name/
   section/sheet. SQLite поддерживает поиск для разработки и тестов.
5. Связать технические источники с товарами по коду, SKU и нормализованному
   названию. Номер вроде «620» сам по себе не доказывает связь: нужны также
   бренд, тип материала и однозначность среди кандидатов.
6. Найденные в техническом материале коды проверить в том же доступном каталоге.
   Для аналогов расширить поиск назначением исходного товара. Общая категория
   без дополнительного подтверждения назначения не считается основанием замены.
7. Передать модели ограниченный контекст: до шести товаров и шести технических
   фрагментов, суммарно до 12 000 символов текста. Метаданные источников и
   системные инструкции передаются дополнительно. Каталог целиком не передаётся.
8. Проверить ответ на неизвестные коды, неверные номера источников и
   неподтверждённые числовые параметры. Проверяемые технические числа должны
   находиться в цитируемых технических материалах; цена и количество — в
   цитируемых позициях доступного каталога. Отклонённый ответ заменяется выдержками.

В SQL до LIMIT применяется ограничение по документу. При окончательном отборе
общий вопрос получает максимум один фрагмент одного источника, предметный —
максимум два. Обзорные документы и разные темы учитываются отдельно для вопроса
о бренде. HTML получает меньший вес, но остаётся доступным, включая случай,
когда других источников нет. Сохраняется FTS с русской морфологией и существующие
индексы; простой substring-поиск не заменяет PostgreSQL FTS.

Для «Как его смешивать?» и «Есть аналог?» из предыдущих пользовательских реплик можно восстановить
артикул. Предыдущие ответы модели, цены и остатки не воспроизводятся как новые
доказательства; каталог заново проверяется в текущем доступе пользователя.

## Каталог и права

Переиспользуются product_names, search_products, _scope_products,
_format_product и действующий расчёт цены. Поиск по SKU в AI использует
нормализованный поиск БД без сетевого ES-запроса для каждого кода: кандидаты
затем ранжируются локально. Обычный API сохраняет прежнее ES-ранжирование.

- Активный клиент видит активные товары своего активного дистрибьютора и свою
  цену, включая персональные и брендовые условия через существующий pricing.
- Дистрибьютор видит свой ассортимент; центральный администратор — общий.
- Менеджер, AI-эксперт и курьер не получают через AI доступ к каталогу, которого
  у них нет в обычных `/products/` и `/distributor/stock/`. Техническая база для
  этих ролей продолжает работать как прежде. Новые права этим изменением не выдаются.
- Неактивные товары не предлагаются. Заблокированный клиент не обходит
  существующую проверку доступа к чату.

В модель передаются только разрешённые поля: имя, SKU, бренд, категория,
существующая группа group_name, описание, синонимы, цвет, объём и разрешённые
цена/количество/статус. В Product нет отдельного поля единицы измерения,
подкатегории, структурированных технических характеристик, связей вариантов
или совместимости. Такие поля не выдумываются: group_name не объявляется
автоматически подкатегорией, объём не получает придуманную единицу, технические
характеристики и назначение извлекаются из реального описания и документации.

`EU620`, `EU-620` и `eu 620` имеют общую нормализованную идентичность. Поиск по
части артикула возможен; источник помечается `queryMatch=partial_sku`, и модель
получает инструкцию не выдавать это за точное совпадение. Несуществующий EU-999
не заменяется автоматически похожим существующим SKU.

## Sources и совместимость API

Сохраняются answer, sources, suggestEscalation, sourceId для карточек,
conversationId и messageId. Для каталога добавляется источник:

```json
{
  "type": "product",
  "sourceType": "product",
  "id": "123",
  "productId": "123",
  "title": "Название из каталога",
  "sku": "Реальный SKU",
  "category": "Категория из каталога",
  "brand": "Бренд из каталога",
  "technicalSourceIds": ["document:456"]
}
```

Технический источник может содержать relatedProductIds. Это свидетельство
связи по идентичности, а не утверждение совместимости. Эти же источники вместе
с фактически переданным excerpt сохраняются в AIMessage.sources. Новые поля
не добавлялись в AIConversation, AIMessage и AIMessageFeedback; публикация
исправлений через обратную связь не менялась. Google Drive ingestion и
KnowledgeDocument/KnowledgeChunk не менялись.

## Развёртывание

```bash
python manage.py migrate
python manage.py check
```

Миграция `0063_product_technical_search` пакетами по 500 записей обновляет
существующее search_text, включая описание и группу. Цены, остатки, SKU,
владельцы и остальные бизнес-данные сохраняются. Новых таблиц не требуется.
Обычные save/update/bulk_create/bulk_update поддерживают этот индекс после миграции.
После обновления кода и миграции перезапустить существующий backend штатным способом.

Используются прежние HF_API_TOKEN, HF_CHAT_MODEL, HF_CHAT_URL и HF_CHAT_TIMEOUT.
Классификация и retrieval не делают отдельных LLM-вызовов. Без токена или при
ошибке провайдера возвращаются реальные выдержки, без выдуманного ответа.
Секреты и вопросы не добавляются в новые логи; пишутся intent и счётчики.

Небольшой словарь поиска можно расширить через AI_DOMAIN_SYNONYMS в окружении:

```dotenv
AI_DOMAIN_SYNONYMS={"degreaser":["обезжириватель","degreaser","силиконремувер"]}
```

Значение — JSON-объект со списками строк. Заданный ключ заменяет соответствующую
группу по умолчанию. Это только поисковые синонимы, не технические факты.

## Проверка

Девять обязательных сценариев находятся в api/test_ai_consultant.py. Там же
проверяются workflow, опечатки, части SKU, назначение, поздний технический chunk,
клиентская цена, изоляция дистрибьютора, роли, источники в истории, ограничения
контекста/SQL-запросов, отсутствие изменений каталога, сбой/проверка ответа модели.
api/test_ai_catalog_migration.py проверяет миграцию на 501 позиции.

Финальный прогон: SQLite — 231 тест, успешно (один PostgreSQL-only тест пропущен);
PostgreSQL 16 — 146 тестов, успешно, включая русскую морфологию и миграции.
Django check, makemigrations --check --dry-run и git diff --check прошли.

Регрессия охватывает существующие AI history/feedback, документы, Drive sync,
поиск, миграции, персональные и брендовые цены, скидки, заказы и наценку магазина.
Уточнено старое ожидание в test_shop_markup: архивирование отзывает токен и
возвращает 401, а не 403. Падение воспроизведено на неизменённом HEAD;
авторизация и правила архивирования не изменялись.

Автоматические проверки используют тестовые товары/TDS и подменённый ответ
провайдера. Они проверяют retrieval, права, контекст и отклонение известных
типов неподтверждённых утверждений. Семантическая корректность всех возможных
ответов не доказывается регулярными выражениями: она зависит от точности
документов и работы модели. Для выпуска нужна контрольная оценка на реальных
TDS и выбранном провайдере. Production этим изменением не обновлялся.
