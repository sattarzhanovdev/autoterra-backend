Актуальный ассортимент и версии реферальных условий

`GET /api/products/` читает базу без серверного кеша, ограничивает авторизованного клиента активными товарами его дистрибьютора и возвращает персональные цены. Ответ содержит `Cache-Control: private, no-store`.

`GET /api/catalog-state/` — авторизованный лёгкий endpoint. Возвращает `catalogRevision`, составленный из максимального `Product.updated_at`, количества всех и количества активных товаров дистрибьютора. Partial save, QuerySet.update и bulk_update обновляют timestamp; создание, Excel, ERP, удаление и деактивация меняют ревизию. Запись напрямую SQL в обход Django не является поддерживаемым способом синхронизации.

`POST /api/integration/erp/catalog-sync/` поддерживает прежний JSON-массив как partial sync и новый контракт:

```json
{"fullSync": true, "items": [{"external_id": "erp-1", "sku": "P1", "name": "Товар", "price": "800.00", "quantity": 3, "is_active": true}]}
```

Полный snapshot создаёт/обновляет переданные товары и деактивирует отсутствующие товары только этого дистрибьютора. Partial sync сохраняет все непереданные товары и поля. Присутствующие товары полного snapshot активируются, если `is_active` не передан явно. Пустой валидный full snapshot деактивирует весь ассортимент дистрибьютора. Snapshot с ошибкой любой строки сохраняет успешные обновления, сообщает ошибки и **не выполняет деактивацию отсутствующих**; в результате есть `deactivationSkipped`.

Поля: external_id/externalId, sku, name, description, category, brand, price, quantity, status, is_active/isActive, images, video_url/videoUrl, synonyms и характеристики карточки/упаковки. Денежные значения проверяются через Decimal. Отсутствующие поля partial sync не заменяются значениями по умолчанию. В SyncLog записываются created, updated, deactivated, errors, startedAt, finishedAt, distributorId и syncType. Pull-strategies IntegrationService используют тот же путь записи и логирования.

Flutter проверяет price/stock известных товаров каждые 5 секунд, ревизию ассортимента — каждые 45 секунд. При изменении ревизии обновляет справочники и уже загруженные страницы каталога. При pull-to-refresh и возврате из background выполняет полный refresh. Поиск, действующие фильтры, корзина и scroll controller сохраняются. Исчезнувшие brand/category снимаются. Старые данные остаются видимыми во время запроса и после сетевой ошибки. Недоступный товар остаётся в корзине с предупреждением; превышение остатка и недоступность блокируют submit. Перед отправкой цены/доступность проверяются снова, а backend независимо проверяет остаток при создании заказа.

Версии реферальных условий задаются в Django Admin → «Версии реферальных условий»: effective_from, tiers (JSON-массив пар [оборот, процент]), activity_min. Вступившие в силу версии нельзя редактировать в админке; нужно создать новую версию. Существующие BonusTransaction не переписываются.

Для каждой подтверждённой закупки или выполненного заказа сохраняется ReferralAccrual: источник, дата подтверждения, версия правил, подтверждённый оборот и сумма. Ступень определяется накопленным оборотом конкретного приглашённого на момент операции. Внутри одной версии целевой бонус равен всему обороту, подтверждённому в период этой версии, умноженному на текущую ставку. Новое начисление — только положительная разница между целью и уже начисленным по этой версии (в том числе потраченным или сгоревшим). Например, 100 000 + 100 000 в одной версии: цель 3 000, первая операция 1 000, доначисление 2 000. Новая версия использует отдельную базу: оборот до её effective_from не переоценивается; старые BonusTransaction и ReferralAccrual не изменяются. Суммы исторического ledger без referral_event учитываются как уже начисленные по исходной версии; нулевые legacy_snapshot-маркеры не приводят к повторному начислению. Дата закупки для выбора правил — verified_at, дата заказа — confirmed_at (для старых записей без неё — created_at); начисление за заказ по-прежнему требует fulfilled. Бонусы фиксируются до копейки с ROUND_HALF_UP. Отсутствие начисления за нулевую операцию тоже отмечается событием для идемпотентности.

Миграция 0067 создаёт правила и события, добавляет дату подтверждения закупки и связь BonusTransaction с событием. Миграция 0068 замораживает исходные ставки/минимум из действующих настроек и отмечает существующие подтверждённые источники обработанными. Исторические BonusTransaction не меняются и не доначисляются. Старые события помечены legacy_snapshot; нулевая сумма такого маркера не является перерасчётом старого бонуса. Дальнейшие изменения REFERRAL_BONUS_TIERS не изменяют начисления — нужно создавать новую версию в базе. Команда recalc_referral_bonuses обрабатывает только источники без события, не пересчитывает старый оборот по новым ставкам. Минимум активности при сгорании выбирается по версии на конец соответствующего календарного месяца.
